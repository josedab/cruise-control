# Cruise Control Architecture Overview

## Introduction

Cruise Control is a sophisticated system for automating the operation of large-scale Apache Kafka clusters. It continuously monitors cluster health, detects anomalies, and can automatically or semi-automatically rebalance the cluster to maintain optimal performance and resource utilization.

## High-Level Architecture

![Architecture Overview](diagrams/architecture-overview.mermaid)

Cruise Control consists of five core components:

1. **LoadMonitor** - Collects and aggregates metrics from Kafka brokers
2. **GoalOptimizer** - Generates optimization proposals based on configured goals
3. **Executor** - Safely applies optimization proposals to the Kafka cluster
4. **AnomalyDetectorManager** - Detects cluster anomalies and triggers self-healing
5. **KafkaCruiseControl** - Main coordinator that orchestrates all components

## Component Responsibilities

### 1. LoadMonitor

**Purpose:** Build and maintain an accurate model of cluster state

**Responsibilities:**
- Consume metrics from `__CruiseControlMetrics` topic
- Aggregate metrics into time windows (hourly, daily, weekly)
- Build and update the in-memory ClusterModel
- Provide historical and real-time cluster state

**Update Frequency:** Every 120 seconds (configurable)

**Key Classes:**
- `LoadMonitor` - Main coordinator
- `MetricSampleAggregator` - Aggregates raw metrics
- `ClusterModel` - In-memory representation of cluster state

### 2. GoalOptimizer

**Purpose:** Generate optimization proposals to achieve desired cluster state

**Responsibilities:**
- Execute goals in priority order
- Generate partition reassignment proposals
- Calculate expected impact of proposals
- Validate proposals don't violate hard constraints

**Goal Types:**
- **Hard Goals** - Must be satisfied (e.g., RackAwareGoal, ReplicaCapacityGoal)
- **Soft Goals** - Best-effort optimization (e.g., DiskUsageDistributionGoal)

**Key Classes:**
- `GoalOptimizer` - Main coordinator
- `AbstractGoal` - Base class for all goals (28+ implementations)
- `OptimizerResult` - Contains proposals and statistics

### 3. Executor

**Purpose:** Safely apply optimization proposals to the Kafka cluster

**Responsibilities:**
- Execute partition reassignments via Kafka AdminClient
- Monitor execution progress (ISR status)
- Apply bandwidth throttling
- Handle execution failures and rollback if needed

**Execution Phases:**
1. **Inter-Broker Replica Movement** - Move replicas between brokers
2. **Leadership Movement** - Elect preferred leaders

**Safety Features:**
- State machine prevents concurrent executions
- Progress monitoring with timeout detection
- Bandwidth throttling to limit impact
- Automatic rollback on critical failures

**Key Classes:**
- `Executor` - Main coordinator
- `ExecutionTaskManager` - Manages individual tasks
- `ExecutionTask` - Represents a single partition movement

### 4. AnomalyDetectorManager

**Purpose:** Detect cluster anomalies and trigger self-healing

**Responsibilities:**
- Run anomaly detectors periodically
- Trigger self-healing actions for detected anomalies
- Report anomalies via configured notifiers

**Built-in Detectors:**
- `BrokerFailureDetector` - Detects broker failures
- `GoalViolationDetector` - Detects goal violations
- `DiskFailureDetector` - Detects disk failures
- `MetricAnomalyDetector` - Detects metric anomalies
- `TopicAnomalyDetector` - Detects topic anomalies

**Self-Healing Actions:**
- Fix goal violations automatically
- Demote failed brokers
- Rebalance after broker failures

### 5. KafkaCruiseControl

**Purpose:** Main facade that coordinates all components

**Responsibilities:**
- Initialize and start all components
- Handle REST API requests
- Coordinate rebalance operations
- Manage execution state

**Design Pattern:** Facade pattern - provides simplified interface to complex subsystem

## Data Flow

![Data Flow](diagrams/data-flow.mermaid)

### Background Processes

1. **Metrics Collection (Continuous)**
   - Kafka brokers collect JMX metrics via `CruiseControlMetricsReporter`
   - Metrics published to `__CruiseControlMetrics` topic
   - LoadMonitor consumes and aggregates metrics every 120s

2. **ClusterModel Updates (Every 120s)**
   - LoadMonitor builds/updates in-memory ClusterModel
   - Historical data retained for multiple time windows
   - Model used by all optimization operations

### User-Initiated Rebalance

1. **Request Phase**
   - User submits rebalance request via REST API
   - KafkaCruiseControl validates no execution in progress
   - State changes to `GENERATING_PROPOSALS`

2. **Optimization Phase**
   - GoalOptimizer receives current ClusterModel
   - Each goal optimizes the model in priority order
   - Proposals generated by diffing initial vs. final state

3. **Execution Phase**
   - Executor receives proposals and begins execution
   - Phase 1: Inter-broker replica movements
   - Phase 2: Leadership elections
   - Progress monitored until completion

4. **Completion**
   - User polls `/user_tasks` endpoint for status
   - Final status: `COMPLETED` or `STOPPED_WITH_ERROR`

## Key Design Decisions

### In-Memory ClusterModel

**Decision:** Keep entire cluster state in memory

**Rationale:**
- Fast access for optimization algorithms
- Enables complex "what-if" analysis
- Simplifies goal implementation

**Trade-offs:**
- Memory usage: ~250KB per replica
- For 1M partitions (3x replication): ~750GB RAM required
- Mitigated by lazy loading and pruning historical data

### Goal-Based Optimization

**Decision:** Pluggable goal architecture with priority ordering

**Rationale:**
- Extensible - users can add custom goals
- Flexible - different priorities for different use cases
- Composable - goals can build on each other

**Trade-offs:**
- Goals may conflict with each other
- Ordering matters significantly
- Can be slow for many goals

### Separate Optimization and Execution

**Decision:** Generate proposals first, execute separately

**Rationale:**
- Safety - review proposals before execution
- Testing - can validate proposals without execution
- Flexibility - can modify proposals manually

**Trade-offs:**
- Cluster state may change between proposal and execution
- Requires state management for long-running operations

## Performance Characteristics

### LoadMonitor

- **ClusterModel Build Time:** O(brokers × partitions)
- **Typical:** 30-60 seconds for 1000 brokers, 100K partitions
- **Memory:** ~250KB per replica

### GoalOptimizer

- **Optimization Time:** O(goals × brokers × partitions)
- **Typical:** 2-5 minutes for 28 goals, 1000 brokers, 100K partitions
- **Memory:** 2x ClusterModel size (original + optimized)

### Executor

- **Execution Time:** Depends on data volume and throttling
- **Typical:** 10-60 minutes for large rebalances
- **Bandwidth:** Configurable throttling (default: 10 MB/s per broker)

## Extension Points

Cruise Control is designed to be extensible:

1. **Custom Goals** - Implement `AbstractGoal` to add new optimization strategies
2. **Custom Anomaly Detectors** - Implement `AnomalyDetector` interface
3. **Custom Metric Samplers** - Implement `MetricSampler` interface
4. **Custom Notifiers** - Implement `Notifier` interface for custom alerting

See [Developer Guide](../developer-guide/custom-goals.md) for implementation details.
